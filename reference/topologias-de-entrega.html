Topologias de entrega

As quatro formas de entregar o mesmo sistema para várias oficinas, o que cada uma custa, e o gatilho que indica que chegou a hora de trocar. Feito para consulta rápida.

Vocabulário

Tenant (inquilino)
Uma oficina cliente. A unidade de isolamento do negócio. No Garage_API, corresponde a uma linha em Oficina.

Deployment / stamp
Um conjunto rodando de infraestrutura — API mais banco. Um stamp pode conter um tenant ou muitos. Tenant é conceito de negócio; stamp é conceito de infraestrutura. Confundir os dois é a origem da maior parte da confusão sobre multi-tenancy.

Tenant resolution
O ponto do código que responde “de qual oficina é esta requisição?”. Pode vir do login, do subdomínio, de um header ou da configuração da instância. Existir em um único lugar é o que mantém a topologia trocável.

Noisy neighbor
Um tenant consumindo recursos a ponto de degradar os outros. Só existe em stamps compartilhados.

As quatro topologias

Topologia Como é Custo por oficina Custo operacional Quando serve
Single-tenant automatizado
o seu plano		 Uma API e um banco por oficina, provisionados por script. Alto e linear.
100 oficinas ≈ 100×.		 Alto. Cada migration roda N vezes. Poucos clientes, ticket alto, exigência forte de isolamento.
Totalmente multitenant Uma API e um banco para todas, separadas por OficinaId. Baixo.
Escala sublinear.		 Baixo. Uma migration serve todas. Muitos clientes de ticket baixo. O perfil da oficina de bairro.
Particionado horizontal API única compartilhada, banco separado por oficina. Médio. Médio. Um deploy de app, N bancos. Meio-termo: isolamento de dados sem frota de servidores.
Particionado vertical Maioria no compartilhado; instalação dedicada para quem paga por isso. Misto. Alto. O código precisa suportar os dois modos. Quando aparece uma rede ou concessionária exigindo dedicado.

Classificação conforme Tenancy Models for a Multitenant Solution, Azure Architecture Center.

A regra que resume a tabela

Topologia resolve isolamento entre organizações. Autenticação e autorização resolvem isolamento dentro de uma organização. Nenhuma das duas substitui a outra, e a segunda é obrigatória em qualquer topologia.

Gatilhos para trocar de topologia

  • Passou de ~5 instalações e a migration virou tarde inteira → automatize com deployment rings, ou migre para banco compartilhado.
  • O custo de infra por oficina se aproxima da mensalidade cobrada → o modelo dedicado deixou de fechar. Vá para compartilhado.
  • Apareceu uma rede com filiais querendo relatório consolidado → banco por oficina passa a atrapalhar; considere particionamento vertical.
  • Um cliente exige isolamento contratual explícito → mantenha dedicado só para ele e cobre por isso.

Checklist antes de instalar para a primeira oficina paga

  • Existe login, e o mecânico não alcança /api/financeiro.
  • A identidade da oficina vem de configuração, não de OficinaConstants.cs.
  • A connection string sai do appsettings.json versionado e vai para variável de ambiente ou secret.
  • CORS restrito à origem do front daquela oficina, não AllowAnyOrigin().
  • Existe rotina de backup do banco e ela já foi restaurada uma vez em teste.
  • Aplicar uma migration em todas as instalações é um comando, não um roteiro manual.
