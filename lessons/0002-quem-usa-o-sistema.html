Lição 02 · Garage_API

Quem realmente usa o sistema

Antes de escrever uma linha de autenticação, a pergunta é outra: quantos tipos de gente tocam nessa API? Errar essa lista é o que obriga a refazer o login seis meses depois — e a lista do Garage_API tem um ator que não é papel nenhum.

O primeiro trabalho do login não é o que parece

A intuição diz que login existe para separar dono de mecânico. Numa oficina de bairro, isso é secundário. O dono está no balcão, são três pessoas, todo mundo se conhece.

O primeiro trabalho do login ali é fechar o perímetro. No instante em que você sobe a instalação num servidor, a API fica na internet, e hoje GET /api/financeiro devolve o faturamento inteiro para qualquer pessoa que descubra o endereço. Não há senha a quebrar, porque não há senha.

Reordene as prioridades

Autenticação (quem é você) resolve o perímetro e é urgente hoje. Autorização (o que você pode fazer) resolve a separação interna e pode começar simples. Muita gente trava meses desenhando papéis elaborados enquanto a API segue aberta — o inverso exato da ordem de risco.

Três categorias de ator, não dois papéis

Mapeando quem toca no Garage_API de verdade:

1. Quem opera a oficina

Dono, recepção, mecânico. São usuários com conta e senha, funcionários daquela instalação. Aqui sim cabe papel — e provavelmente dois, não cinco.

2. Você, que vende e mantém

Alguém precisa cadastrar a oficina na instalação nova. POST /api/Oficina e o cadastro de mecânicos são operações de implantação, não do dia a dia. Se ficarem no mesmo balcão que o resto, o cliente vai mexer e quebrar.

3. O dono do carro

Esse é o que quebra o modelo de papéis. O README lista “link de aprovação para cliente” como próxima evolução, e os endpoints POST /api/ordens-servico/{id}/aprovar e /recusar já existem, abertos. No dia em que o link for enviado por WhatsApp, um estranho — sem conta, sem senha, que nunca vai criar uma — precisa alcançar aquele endpoint. E só aquele.

A armadilha exata

A saída óbvia é mandar o link com o GUID da OS: /aprovar/3f2a.... Isso transforma um identificador em credencial — e são coisas diferentes. Identificador aparece em log de servidor, em histórico de navegador, no Referer, na conversa encaminhada para o grupo da família. Quem tiver o GUID aprova a ordem, e a aprovação é o que autoriza a oficina a cobrar.

O que esse ator precisa é de um token de capacidade: gerado por OS, com validade, revogável quando a ordem sai do estado AguardandoAprovacao, e que não dá acesso a mais nada. Não é papel. Não entra na tabela de usuários.

Quantos papéis, afinal

Para a categoria 1, a tentação é modelar dono, gerente, recepcionista, mecânico, auxiliar. Numa oficina de três pessoas, isso é atrito puro: mais telas de cadastro, mais senha esquecida para você atender no telefone, mais motivo para o dono desistir e pedir “me dá um login que vê tudo”.

A documentação da Microsoft é direta sobre a limitação: papéis “são uma forma fácil de agrupar usuários, mas não são muito expressivos”. A recomendação é usar políticas nomeadas quando a regra passa de trivial.

Para o seu caso isso se traduz em algo pequeno e defensável: dois papéis — quem vê dinheiro e quem não vê — expressos através de políticas nomeadas. A política é o seam: [Authorize(Policy = "VerFinanceiro")] no controller, e a definição da regra num único ponto do Program.cs. No dia em que uma oficina maior pedir um perfil de recepção, você muda a definição da política, não quarenta e quatro controllers.

O mesmo princípio da lição 01

Na lição anterior, a conclusão foi resolver a identidade da oficina num único ponto para poder trocar de topologia depois. Aqui é a mesma ideia noutro eixo: expressar a permissão num único ponto para poder trocar o modelo de papéis depois. Decisão que você ainda não tem como tomar bem vira um ponto de indireção, não uma escolha precipitada espalhada pelo código.

A escolha de mecanismo, e a pegadinha dela

O caminho mais curto em .NET 10 é ASP.NET Core Identity com MapIdentityApi: ele já entrega registro, login, refresh e recuperação de senha, e conversa bem com o front em React que você já tem. Para uma instalação por oficina, é proporcional ao problema.

Leia isto antes de adotar

A própria documentação avisa: os tokens emitidos não são JWT padrão. São proprietários do Identity, e a escolha é intencional — a API embutida é feita para cenários simples, não para ser um servidor de identidade completo.

Consequência prática: enquanto você vender instalação isolada para oficina de bairro, isso não incomoda. Se um dia aparecer rede ou concessionária pedindo login único corporativo, esse token não federa e a troca é retrabalho. Adote sabendo o teto.

Fonte primária para ler agora

Use Identity to secure a Web API backend for SPAs — Microsoft Learn, versão ASP.NET Core 10.0. É o caminho exato do seu caso: API .NET com front SPA em React. Preste atenção à seção sobre tokens, que explica por que eles não são JWT.

Pergunte. Os pontos que costumam ficar vagos aqui: como o token de aprovação do cliente é gerado e revogado na prática, se dois papéis realmente bastam para o seu primeiro cliente, ou como isso muda quando a oficina tem recepcionista dedicada. Qualquer um deles vira a próxima conversa.
